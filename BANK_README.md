## File format

`memory_bank.jsonl` — **one JSON object per line** (JSON Lines):

```json
{"kind": "general", "q": "What is the capital of France?", "a": "Paris."}
{"kind": "daily", "fact": "Drink about 2 litres of water a day."}
```

Rules:
- `q` + `a` for questions; `fact` for standalone facts.
- **Append-only.** Never rewrite the file in place; only append new lines.
- **No duplicates.** A question/fact counts as duplicate when its
  normalised form (lowercase, punctuation stripped, whitespace
  collapsed) already exists — regardless of kind.
- **Only accurate facts.** Never invent a number, date or name you are
  not sure of. If unsure, skip that entry — a missing entry is better
  than a wrong one.
- One line = one entry. No blank lines. UTF-8, no BOM.

## How the bot uses it (`bank.py`)

- `bank.load()` **streams** the file line by line (never reads it whole
  into memory) and builds a compact lookup index. Malformed lines are
  **skipped and counted** — a torn last line (e.g. an interrupted
  write) never crashes the bot. Verified: a file with a chopped last
  line + a garbage line still loads, reports 2 skipped lines, and
  keeps answering.
- `bank.lookup(text)` — exact match on the normalised question first,
  then a keyword fallback (the entry sharing the most content words
  wins, only if it matches ≥ 2 content words or every content word
  of a short question).
- `brain.respond()` checks the bank after taught answers and personal
  facts, before jokes and the "I don't know" fallback. All built-in
  behaviour (greetings, time, date, calculator) is untouched.
- `/memory` shows a compact gauge; `/brain` shows the full brain-chips
  display (total, bar toward 1,000,000, per-kind counts).
- Scale design: streaming load + dict index works to 1,000,000+
  entries. At full size the index holds ~1M short strings in memory
  (a few hundred MB) — acceptable on any normal computer; the file
  itself stays a plain `.jsonl` that any tool can read.

## Progress file (`bank_progress.json`)

Regenerated by every generator run (atomic temp-file + rename):

```json
{"total": 300, "per_kind": {"general": 50, ...}, "capacity": 1000000,
 "goal": 950000, "per_kind_goal": 150000,
 "last_batch_id": "batch-001", "last_batch_added": 1, "malformed_lines": 0}
```

`total` is always recomputed by recounting the file — the progress
file never invents a number.

## How to continue the grind (resume brief)

1. Copy `gen_batch1.py` to `gen_batchN.py` (next free number).
2. Change `BATCH_ID` (e.g. `"batch-002"`) and replace `ENTRIES` with
   new entries — **recommended batch size 500–1,000 per run**, spread
   across all 6 kinds (roughly even, or fill the kind furthest behind).
3. Run `python3 gen_batchN.py`. It dedupes against the bank file
   (re-runs are safe: already-present entries are skipped) and
   refreshes `bank_progress.json`.
4. Verify: `wc -l memory_bank.jsonl` must equal the `total` in
   `bank_progress.json`, and `python3 octo.py "a new bank question"`
   must answer from the new batch.
5. Keep the generator files in the repo — they are the audit trail of
   where every entry came from.

**Real pace:** each batch is written by hand (or by a careful agent
run) at ~500–1,000 entries. Reaching 950,000 needs roughly
**950–1,900 batches** at that size. That is a long grind — weeks of
steady batches, not one afternoon. The system is built to survive it
(resumable, idempotent, verified per batch); the count only ever
claims what the file actually holds.
